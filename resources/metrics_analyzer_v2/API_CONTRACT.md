## 1. Overview (Part A)

### 1.1 Scope

V2 is additive. The existing application, its `/api/v1/dq/*` and `/api/v1/tr/*` routes, its investigation jobs and its fallback assets keep working unchanged. V2 adds a new frontend at `/` and two new backend routers in the same FastAPI service. There is no second backend service. Cloudflare Pages, the Oracle VM, Docker, Nginx and FastAPI stay. (VERIFIED: current stack from `README.md`, `backend/README.md`, `backend/Dockerfile`.)

### 1.2 Base path, namespaces, versioning (PROPOSAL)

The browser already reads one variable, `VITE_API_BASE_URL`, whose value ends in `/api/v1` (VERIFIED: `README.md`, `frontend/src/backend/services/httpApi.ts` line 27 onwards). V2 reuses that variable and appends a new namespace. No new frontend variable and no URL rewriting is needed.

| Namespace | Full path | Purpose |
| --- | --- | --- |
| Portfolio | `${VITE_API_BASE_URL}/portfolio/*` | Deterministic reads over `METRICS_ANALYZER.MOCK_DATA`. No LLM. |
| Agents | `${VITE_API_BASE_URL}/agents/*` | Agent metadata, context review, conversations, runs. |

Neither namespace collides with `/api/v1/dq/*` or `/api/v1/tr/*`. "V2" names the product and the contract. It is not in the URL. The contract version is returned in every response as `meta.contractVersion`. A breaking change adds a new namespace version (`/api/v2/...`); additive changes (new optional fields, new enum values the client must tolerate) keep `2.x`.

### 1.3 Compatibility with the existing API

- Legacy routes, response shapes and error bodies (`{ "code", "message" }`) are untouched.
- V2 uses its own envelope (section 3.1) and its own error shape (section 3.2). A V2-only exception type and a V2-scoped validation handler produce it. The global handlers in `backend/app/main.py` are not edited.
- The only edit to existing backend wiring is one call, `register_v2(app)`, which includes the two new routers (and registers the start-up check). CORS is unchanged: methods stay `GET` and `POST`, allowed headers stay `Content-Type` (no custom header is used). (VERIFIED current CORS: `allow_methods=["GET","POST"]`, `allow_headers=["Content-Type"]`.)

### 1.5 Runtime identity for the new integration (REVISED)

VERIFIED facts about the existing backend:

- `Settings.snowflake_role` defaults to `ACCOUNTADMIN` in code (`backend/app/config.py`), and `backend/.env.example` sets `SNOWFLAKE_ROLE=ACCOUNTADMIN`. Every existing connection (`connect`, `connect_read`) opens its session with the configured role.
- The credentials in `backend/.env` are a personal named user's. The deployed `.env` was deliberately not read for this document.
- Earlier validation created a demo role `METRICS_ANALYZER_DEMO_VIEWER` (granted to user `METRICS_ANALYZER_VIEWER`) with read access to `APPLICATION_COMPLIANCE`, `V_APPLICATION_MONTH_STATUS`, `SV_APPLICATION_COMPLIANCE_V1` and usage of both agents. Nothing in the backend uses it.

**Decision (project owner, applies to V2; DEC-04).** The Snowflake account is a temporary demo account. V2 uses the backend's existing Snowflake login and connection helper (`Settings`, role from `backend/.env`, ACCOUNTADMIN) exactly as the legacy routes do. The earlier proposal of a pinned least-privilege role, `USE SECONDARY ROLES NONE` and a start-up role self-check is withdrawn. The risk (an administrator-level login held by a public API) is accepted for this demo and recorded as `OI-01`; it must be revisited before any non-demo use.

What this changes and what it does not:

1. V2 opens connections with `app.db.connection.connect(settings)` (no new connection module). It never runs `USE ROLE`.
2. V2 SQL is read-only by construction: only `app/portfolio/repository.py` contains Portfolio SQL, it contains `SELECT` statements only, identifiers come from enumerations and values are bound parameters (a test asserts no DDL or DML keyword and no string-built values). Deterministic reads still use `V_APPLICATION_MONTH_STATUS` and `APPLICATION_COMPLIANCE`, the objects whose results were verified against the exports; the snapshot table and organisation view may be read by reconciliation tests only.
3. The only Snowflake changes V2 makes, both in the implementation phase and only after the owner's approval of the generated script: agent specification v2 (5.8) and the one-off generation of the precomputed investigation files (6.7, which is read-only SQL through the agents). No schema, table, dataset or MCP server is created or changed.
4. Writes at runtime: V2 writes no table and has no store of its own. Conversations are Snowflake Cortex Agent threads, created and filled by the agent calls themselves (5.7).
5. Credentials never leave the backend: not in the bundle, not in responses, not in logs (3.8).
6. The two agents are invoked with `SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN(<agent>, <body>, TRUE)`, the call already proven in `backend/app/cortex/agent_client.py`. The agent object name comes from server constants, never from the request. The legacy `agent_client` is not reused, because it has its own semaphore and `Settings.cortex_agent`.

### 2.2 Grain rules (binding for every endpoint)

| Rule | Statement |
| --- | --- |
| G-1 | `EON_ID` is an application. `METRIC_ID` is a metric. A metric row is one application's observation of one metric at one month-end. |
| G-2 | Application counts come from `V_APPLICATION_MONTH_STATUS`, or `COUNT(DISTINCT EON_ID)` on `APPLICATION_COMPLIANCE`. Never `COUNT(*)` of metric rows. |
| G-3 | Metric-level detail comes from `APPLICATION_COMPLIANCE`. Because the key is unique, per metric and month the number of rows equals the number of applications. |
| G-4 | Historical trends keep the historical application-month records. A current roll-up that spans months (for example "all applications") uses each application's latest month. A single-month view uses that month's rows. |
| G-5 | `TOTAL_RFB` repeats on every metric row of an application-month. It is never summed across metric rows. Open findings for an application-month is `MAX(TOTAL_RFB)` (the view column `OPEN_FINDINGS`). A portfolio total is the sum of those per-application values for one month. `RFB` is a row-level count and may be summed only within one metric. |
| G-6 | `BUSINESS_ORG` (`SUPER_DIVISION`, `DIVISION`, `SUPER_DEPARTMENT`, `DEPARTMENT`, `BUS_ORG_LG_NM`) and `BU` (`BU_SUPER_DIVISION`, `BU_DIVISION`, `BU_SUPER_DEPARTMENT`, `BU_DEPARTMENT`) are separate trees. They are never joined, merged or shown in one hierarchy. Default is `BUSINESS_ORG`. |
| G-7 | Risk is grouped by the stored `ASSET_RISK_RATING_2` code (values observed: P1, P2, P3, P4). Tier is the stored number 1–4. Neither has a defined direction, so the API never ranks them as better or worse and never invents a score. Results are ordered by code. |
| G-8 | An application that is not non-compliant is not "compliant". `Compliant`, `Non_Compliant`, `Pending` and `Not_Applicable` stay separate. |
| G-9 | Missing is not zero. A month in which an application did not report is returned as "not observed", never as a zero or as compliant. |
| G-10 | The first month in the data has no prior month. Movement fields for it are `null`, not `0`. |

### 2.4 Provisional definition registry (PROPOSAL)

All derived analytics are defined once, in a single backend module (`app/portfolio/definitions.py`) that is the only place formulas live. Every endpoint, both agent context builders, the agent specification text and the frontend chips read ids from it. `GET /portfolio/definitions` publishes it. The registry carries a version, `definitionsVersion` (`pd-1` at first release), returned in `meta.definitionsVersion` of every response; any change to a definition requires a new version (a snapshot test enforces this). Source columns stay raw; nothing is stored back.

Status values: `source` (raw column or count), `documented_rule` (a rule recorded in the assumptions register or view comment), `provisional` (depends on an unconfirmed business meaning), `assumption` (a classification the design infers; not in the source), `not_available`.

| Id | Name | Definition | Status | Basis |
| --- | --- | --- | --- | --- |

## 3. Common standards (Part E)

### 3.1 Response envelope

Every successful V2 response is JSON with this shape. Field names are camelCase. (PROPOSAL)

```ts
interface Envelope<T> {
  data: T
  meta: {
    contractVersion: '2.0.0'
    definitionsVersion: string        // registry version, section 2.4 (for example 'pd-1')
    requestId: string                 // hex, also logged
    generatedAt: string               // ISO-8601 UTC, e.g. 2026-11-04T09:15:02Z
    asOf: string | null               // resolved month-end used (YYYY-MM-DD), null if not month-scoped
    dataset: { version: string; rowCount: number; promotedAt: string | null }
    source: 'snowflake' | 'packaged'  // 'packaged' = degraded fallback (section 3.9)
    cache: { hit: boolean; ageSeconds: number; ttlSeconds: number }
    warnings: Array<{ code: string; message: string }>
    lineage?: Lineage[]               // see 3.4; omitted where the endpoint lists definitions inline
  }
}
```

`dataset.version` is `v1-seed20261103` (VERIFIED value). `dataset.rowCount` and `promotedAt` come from a cheap probe of `APPLICATION_COMPLIANCE` (`COUNT(*)`, `MAX(PROMOTED_AT)`), cached for 10 minutes.

### 3.2 Error shape

```ts
interface ApiErrorBody {
  error: {
    code: string                      // stable, UPPER_SNAKE
    message: string                   // safe to show
    retryable: boolean
    requestId: string
    retryAfterMs?: number
    fieldErrors?: Array<{ field: string; code: string; message: string }>
    details?: Record<string, unknown> // never SQL text, never stack traces, never secrets
  }
}
```

| HTTP | Codes | Retryable |
| --- | --- | --- |
| 400 | `VALIDATION_FAILED`, `UNKNOWN_MONTH`, `UNKNOWN_FILTER_VALUE`, `UNSUPPORTED_SORT`, `CONTEXT_TOO_LARGE`, `MESSAGE_TOO_LONG`, `CONTEXT_INVALID` | no |
| 404 | `METRIC_NOT_FOUND`, `APPLICATION_NOT_FOUND`, `CONVERSATION_NOT_FOUND`, `RUN_NOT_FOUND` | no |
| 409 | `RUN_IN_PROGRESS`, `RUN_NOT_RETRYABLE`, `CONTEXT_STALE`, `IDEMPOTENCY_KEY_REUSED` | no (state change needed) |
| 429 | `AGENT_BUSY`, `RATE_LIMITED`, `AGENT_BUDGET_EXHAUSTED` | yes, with `retryAfterMs` |
| 502 | `UPSTREAM_ERROR` | yes |
| 503 | `DATA_SOURCE_UNAVAILABLE`, `AGENT_UNAVAILABLE`, `THREAD_UNAVAILABLE`, `FALLBACK_UNSUPPORTED` | yes (except `FALLBACK_UNSUPPORTED`) |
| 504 | `UPSTREAM_TIMEOUT` | yes |

`401` and `403` are not used. The existing API has no end-user authentication and V2 adds none; a handle or token that does not verify is reported as `404` (section 3.8).

Unexpected exceptions map to `502 UPSTREAM_ERROR` with a generic message, as the legacy handler does, and are logged by exception type only.

### 3.3 Validation

- All inputs are validated at the edge. Unknown query parameters are ignored but listed in `meta.warnings` (`UNKNOWN_PARAMETER`).
- `month` must be a known month-end from `GET /portfolio/filters` (`UNKNOWN_MONTH`).
- Multi-value parameters repeat the key (`risk=P1&risk=P2`), at most 50 values, each at most 100 characters, each validated against the filters allow-list (`UNKNOWN_FILTER_VALUE`). `l1`/`l2` values are validated against the chosen `orgTree`.
- `metricId` must match `^M[0-9]{6}$` and exist. `eonId` must match `^EON[0-9]{6}$` and exist. Unknown ids return 404, not an empty 200.
- Free text (`q`, `message`) is length-limited: `q` 40 characters; `message` 2,000 characters.
- All values reach SQL as bound parameters. Column names, sort fields and `breakdown` dimensions come from code allow-lists only. No request value is concatenated into SQL.

### 3.4 Lineage object

```ts
interface Lineage {
  field: string                       // dotted path in `data`, e.g. "kpis.nonCompliant.share"
  class: 'observation' | 'derived' | 'hypothesis'
  status: 'source' | 'documented_rule' | 'provisional' | 'assumption' | 'not_available'
  definitionIds: string[]             // PD-xx
```

### 3.5 Pagination, sorting, filtering

- Pagination: `page` (1-based, default 1) and `pageSize` (default 25, maximum 100), the same names the legacy API uses.
- Response page block: `{ page, pageSize, totalItems, totalPages }`.
- Sorting: `sort=<field>:<asc|desc>`, one field. The field must be on the endpoint's allow-list. A fixed tie-breaker (stated per endpoint) makes ordering stable across pages. Unknown field gives `400 UNSUPPORTED_SORT`.
- Filtering uses the shared scope filters below.
- Out-of-range page returns 200 with an empty `items` and correct `totalItems`.

Shared **scope filters** (applied at application-attribute level; valid at both grains because application attributes are constant within an application-month, VERIFIED: 0 violations):

| Parameter | Type | Column(s) |
| --- | --- | --- |
| `month` | `YYYY-MM-DD` month-end, default latest | `REPORTING_MONTHEND_DATE` |
| `orgTree` | `BUSINESS_ORG` (default) or `BU` | see G-6 |
| `l1` | repeat | `SUPER_DIVISION` or `BU_SUPER_DIVISION` |
| `l2` | repeat | `DIVISION` or `BU_DIVISION` |

### 3.6 Dates, times, numbers, nulls

- Dates are `YYYY-MM-DD` and always month-ends. Timestamps are ISO-8601 UTC with `Z`. The snapshot extract carries a `-08:00` offset; the API normalises to UTC.
- Counts are JSON integers. Rates and shares are JSON numbers between 0 and 1 rounded to 6 decimal places by the backend; the frontend only formats. Percentage-point deltas are rounded to 4 decimal places. The frontend never recomputes a rate.
- Snowflake `NUMBER` values are converted to integers when scale is 0, otherwise to decimals; never strings, except in agent result sets (section 6.2) where cells are returned as the agent tool returned them.
- Missing is `null`. A division by zero is `null`. `0` always means a counted zero.
- A month without observations for an application or metric appears in `history` arrays as `{ "month": "...", "observed": false }` and nothing else.

### 3.7 Correlation, timeouts, retry

- `requestId` is generated per request, returned in `meta.requestId` or `error.requestId`, and logged. It is not accepted from the client.
- Deterministic reads use the existing 5-second read budget pattern (`begin_read_deadline`). Exceeding it triggers the fallback path where one exists, otherwise `504 UPSTREAM_TIMEOUT`.
- The browser wrapper keeps the legacy behaviour: 20-second timeout and one retry on `GET`. `POST` is not retried automatically. Creating a message is protected by `clientRequestId` (section 5.5.5) so a manual retry cannot duplicate it.
- Agent calls never block an HTTP request or the event loop: every V2 route is a plain `def` handler and the long agent work runs inside Snowflake as a background run (section 5.5.3).

### 3.8 Authentication, authorisation and privacy (PROPOSAL, DEC-14; REVISED)

**What exists today (VERIFIED).** No file in `backend/app` implements authentication: there is no `Depends`-based guard, no API key, no bearer or session handling. The only access control is CORS (`allow_origins` from `CORS_ORIGINS`, `allow_credentials=False`), which a browser enforces and any other HTTP client ignores. The legacy endpoints, including the ones that start Cortex investigations, are therefore publicly callable on the backend host. No Cloudflare Access, WAF or Nginx authentication configuration is in the repository, and the VM's Nginx was not inspected (plan section I, gate V-3). CORS allowed headers are not authentication and are not treated as such here.

**What V2 enforces without a database, without new infrastructure and without any secret in the frontend bundle.**

1. **Portfolio (`/portfolio/*`)**: read-only deterministic data, public, exactly like the legacy read endpoints. Protected by CORS, the read deadline, the response cache and the circuit gate. No credential is needed.
2. **Agents (`/agents/*`)**: access to a conversation or a run requires its **signed handle or token**, a capability string that only the backend can produce.
   - `conversationId` = `v1.<base64url(JSON {threadId, agentKey, createdAt})>.<base64url(first 16 bytes of HMAC-SHA256)>`.
   - `runId` = `v1.<base64url(JSON {threadId, agentKey, userMessageId, snowflakeRunId, submittedAt})>.<signature>`.
   - The signing key is derived at start-up from the Snowflake password the backend already holds (`HMAC-SHA256(password, "ma2-signing-v1")`), so no new environment variable or secret is introduced. An optional `V2_SIGNING_KEY` environment variable may override it; it is not required. A key change (for example rotating the Snowflake password) makes every previously issued handle read as `404 CONVERSATION_NOT_FOUND`; the threads themselves are unaffected.
   - A request with a handle whose signature does not verify, or whose `threadId` or `agentKey` was edited, returns `404 CONVERSATION_NOT_FOUND` (`RUN_NOT_FOUND` for runs), the same as a missing id. A Snowflake thread id (a plain integer) is never accepted as authority.
   - The agent used for a follow-up is the one inside the handle. The request body cannot choose or change it.
3. **What this does and does not provide (stated plainly).** It prevents guessing or editing another conversation's identifiers and keeps the browser from choosing agents or threads. It is not user authentication and not per-user ownership: whoever holds a handle can use the conversation, and anyone who can reach the API can start a new one. For this demo that is the decision (DEC-16, plan D.4): no end-user login. The code keeps a single seam, a `get_principal` dependency, so a later mechanism would be one dependency and would not change the routes.
4. **Abuse and cost controls** (public endpoints can spend Snowflake credits; the legacy ones already can). All in memory, per process, reset at restart (OI-14): runs per handle 10 per 10 minutes (`429 RATE_LIMITED`); new conversations from all callers 20 per 10 minutes (`429 RATE_LIMITED`); runs across all callers 60 per hour and 300 per day (`429 AGENT_BUDGET_EXHAUSTED`, with `retryAfterMs`); 4 runs in flight (`429 AGENT_BUSY`); a per-IP limit is added only if the proxy forwards the client address (plan gate V-4).
5. **Credentials.** The browser never receives Snowflake credentials, role names, agent names, SQL or any server secret. The Snowflake login used by V2 is the backend's existing one from `backend/.env` (ACCOUNTADMIN on a temporary demo account, accepted by the project owner; see 1.5 and OI-01). Handles and tokens are capabilities held by the browser; they are never logged (only their hash prefix).
6. **Privacy.** Owner names (`PRIMARY_BUS_*`, `PRIMARY_IT_*`) are fictional but treated as personal-looking. They are returned only when `includeOwners=true` and are put into agent context only when the user switches the `owner_names` item on. Logs never contain message text, rendered context, result rows, handles or secrets; they record lengths and hashes.

### 3.9 Caching and fallback

- Deterministic responses are cached in the API process, keyed by endpoint, resolved parameters and `dataset.promotedAt`, for 600 seconds (the data are static per dataset version). `meta.cache` reports hit, age and TTL. Frontend caching follows the existing `useQuery` freshness window (60 seconds) and is separate.
- A new circuit gate (`portfolio_gate`, 30-second cooldown, same pattern as `snowflake_gate`) switches Portfolio reads to packaged data after a dependency failure. It does not share state with the legacy gates.
- Packaged fallback (`meta.source = "packaged"`) exists only where a verified extract exists today: `overview`, `trends`, `distributions/testing`, `distributions/risk`, `org/contribution` and `applications` for the latest month (Oct 2026) and the default `BUSINESS_ORG` tree with no filters. This follows the JSON files in `snowflake/mock_data_setup/export/`: `overview.json`, `monthly_trends.json`, `testing.json`, `risk_distribution.json`, `org_contribution.json`, `application_register.json`. Filtered requests, other months and every metric-level or application-level endpoint return `503 FALLBACK_UNSUPPORTED` when Snowflake is down. Extending the extracts is optional follow-up work and needs a Snowflake export run by an administrator.
- Precomputed investigation analyses (section 6.7) are a separate, narrower fallback: they apply only to the `agentAnalysis` field of 4.20 and 4.21, carry `source: "precomputed"`, and never to chat conversations. `meta.source` stays `snowflake`.
- Export files use upper-case Snowflake column names (for example `NON_COMPLIANT_APPLICATIONS`). The fallback reader maps them to the contract field names.
- A packaged response carries `warnings: [{ code: "PACKAGED_DATA", message: "..." }]` and the frontend shows a visible notice.
- Agent endpoints have no fallback. When the agent path is unavailable the run fails honestly (section 6.6). Nothing is answered from static text.

### 3.10 Observability

- One access log line per request: route template, status, duration, `source`, cache hit, `requestId`.
- Agent runs log `runId`, `agentKey`, status transitions, elapsed time, number of tool results and Snowflake `query_id`s, and failure code. They do not log message text or rows.
- `GET /portfolio/status` (section 4.1) gives a lightweight health view for the frontend banner.

### 3.11 Compatibility rules

- Clients must ignore unknown fields and tolerate unknown enum values by displaying them verbatim.
- Removing or renaming a field, or changing its meaning, is a breaking change.
- Registry definitions can change status (for example `provisional` to `documented_rule`) without a contract version change; clients must not hard-code the status of a definition.

## 5. Agent endpoints (Part C) (REVISED: Snowflake threads, no application database)

Base: `${VITE_API_BASE_URL}/agents`. Two agents, both entered from two surfaces: the **general** Agent section and **contextual** entry points (Dashboard, Register preview, Metric Summary, both Investigations).

**Architecture in one paragraph (DEC-03, DEC-15).** The backend stores nothing about conversations. A conversation is a Snowflake Cortex Agent **thread**. Messages, tool calls and executed SQL results live in that thread and are read back with `SNOWFLAKE.CORTEX.THREAD_MESSAGES`. Every run, including the first message of a new conversation, is `SNOWFLAKE.CORTEX.DATA_AGENT_RUN` with the third argument `TRUE` and `"background": true`. The call returns in under a second with `status: in_progress` and the ids in `metadata`. The backend then reads the thread until the assistant message whose `parent_id` equals that run's `user_message_id` is present. This was executed on 2026-11-04 for both agents (5.5.3). The browser keeps only a small list of its own conversations in `localStorage` (5.4). The backend keeps only in-memory, rebuildable helpers (5.7). There is no application database, no volume and no new service.

### 5.1 Conventions

- Agent keys are exactly `analysis` and `data`. They are the only agent identifiers the browser knows.
- The server maps `analysis` to `METRICS_ANALYZER.MOCK_DATA.AGENT_APPLICATION_COMPLIANCE_V1` and `data` to `METRICS_ANALYZER.MOCK_DATA.AGENT_APPLICATION_TEXT_TO_SQL_V1` from constants in code (VERIFIED object names). They are never read from a request.
- Verified account facts: region `AWS_AP_SOUTH_1`, Snowflake version `10.40.100`, connection role `ACCOUNTADMIN` (read-only probe, 2026-11-04). The same day, both agents accepted `background: true` and `create_thread_if_not_present = TRUE` (5.5.3).
- No authentication header and no session exist (3.8). Access to a conversation is by its **conversation handle** (`conversationId`), an unguessable signed string (3.8). The CORS configuration is unchanged.
- Mutations are `POST`. There is no `DELETE` and no `PUT`.
- No request contains SQL, an agent object name, a role, a thread id used as authority, or context text. A request that creates a conversation carries a structured **context request** (ids and filters, 5.3) that the server resolves itself.

### 5.3 Context: preview, validation, hand-over (stateless)

Context is what the user hands the agent. It is **built by the server** from verified data using the same services as the Portfolio endpoints and shown in readable form. The backend keeps **no context registry**: the context is recomputed from a structured request when it is previewed and again when the conversation is created, and from then on it lives in the thread.

#### Request

`POST /agents/context/preview`

```ts
interface ContextRequest {
  entrySurface: 'general' | 'dashboard' | 'register_preview' | 'metric_summary' | 'metric_investigation' | 'application_investigation'
  scope: { month?: Month; metricId?: string; eonId?: string; filters?: Partial<ActiveFilters> }   // month omitted = latest available, resolved by the server
  items?: { include?: string[]; exclude?: string[] }       // keys from the catalogue below
}
```

#### Response

```ts
interface ContextPreview {
  contextHash: string                  // sha-256 hex over versions, resolved scope and rendered.text; first 12 characters shown to users
  definitionsVersion: string           // registry version the text was rendered from
  entrySurface: ContextRequest['entrySurface']
  scope: { month: Month; monthSource: 'selected' | 'latest_available'; metricId: string | null; eonId: string | null; filters: ActiveFilters }   // resolved by the server, month never null

  rendered: { text: string; chars: number; approxTokens: number }   // EXACTLY what is sent before the user's question

  key: string; label: string

  included: boolean
  defaultIncluded: boolean
  sensitive: boolean

  lines: string[]                      // up to 12 readable lines (what the agent will read), not JSON
```

The preview stores nothing. The review UI shows `chips`, then each item as a readable block with a switch (disabled for `required`), then a collapsed "Exact text sent" disclosure showing `rendered.text` as plain preformatted text. The UI keeps the `ContextRequest` it used (in memory, and in `sessionStorage` for a refresh of the review step).

#### Item catalogue (PROPOSAL)

| Key | Surfaces | Required | Default | Content |

Items that are not on the surface's list are rejected with `400 CONTEXT_INVALID`. The `general` surface has no metric or application items; to scope it the user uses a contextual entry point.

#### Validation and bounding

- Request bodies are strict (unknown fields are rejected). Identifiers must exist (`METRIC_NOT_FOUND`, `APPLICATION_NOT_FOUND`); `month`, when given, must be a known month-end (`UNKNOWN_MONTH`); filter values must be in the `GET /portfolio/filters` allow-lists.
- `required` items cannot be excluded (`CONTEXT_INVALID`).
- Rendered text is limited to 12,000 characters. Per item: 12 lines, 400 characters per line. Above the cap the call fails with `400 CONTEXT_TOO_LARGE` and `details.largestItems` naming the optional items to remove. Nothing is truncated silently.
- Strings that come from data (application names, group names, metric ids) are sanitised before they enter rendered text: control characters and line breaks are removed and each value is cut at 80 characters with an ellipsis. The user's question never enters the readable lines.

#### Server-side resolution of scope

The server resolves every part of the scope itself; the browser's request is only an input to that resolution.

| Part | Rule |
| --- | --- |
| Month | 1. `scope.month` if supplied (an explicitly selected month always wins). 2. Otherwise the latest reporting month in the dataset, `MAX(REPORTING_MONTHEND_DATE)` of `V_APPLICATION_MONTH_STATUS`, the same value as `GET /portfolio/status.latestMonth`, cached with `dataset.promotedAt`. The month is never defaulted from a constant in code or from an agent's instructions. The resolved `scope.month` is never null, and `scope.monthSource` is `selected` or `latest_available`. The chips and the rendered scope line say "(latest available)" when it was not selected. |
| Metric / application | Looked up and validated; the resolved scope holds the canonical ids. |
| Filters | Validated against the allow-lists, normalised (arrays sorted and de-duplicated, empty values removed) and resolved to `ActiveFilters`; counts shown in the context are computed by the same Portfolio services under those filters. |
| Items | The final included item keys, sorted, after required and default rules. |

#### Integrity without a registry (PROPOSAL, DEC-06)

- **Hash.** `contextHash` is the lower-case hex SHA-256 (64 characters) of the UTF-8 bytes of: `ma2-context-v1`, a line break, `definitionsVersion`, a line break, `dataset.promotedAt` (empty if unknown), a line break, the canonical JSON of the resolved scope plus the sorted included item keys (sorted keys, no whitespace), a line break, `rendered.text`.
- **Verification.** `POST /agents/conversations` carries the same `ContextRequest` and the `contextHash` the user reviewed. The server rebuilds the context from the request, recomputes the hash and compares it in constant time. A mismatch returns `409 CONTEXT_STALE` (the data, the definitions or the request changed since the review) and the UI shows the review again. The browser cannot alter what the agent receives: it sends only identifiers, filters and item keys, never text, and the text is always produced by the server.
- **Authorisation.** Previewing and building a context reads only data that the public Portfolio endpoints already expose, except `owner_names`, which needs `includeOwners` semantics (3.8). Nothing is stored before the conversation exists.
- **Lifetime.** There is no context expiry or invalidation state, because nothing is stored. A context is valid only at the moment of conversation creation; once the first message is in the thread the context is part of the conversation's history and does not change. A later dataset or definitions change affects only new conversations (the conversation view can show "data has changed since this conversation started" by comparing the thread's recorded `definitionsVersion` and dataset version with the current ones).
- **No arbitrary names.** The agent is chosen by `agentKey` from the two constants; the thread is reached only through a signed handle (3.8).

#### How the exact resolved context is passed to each Agent

The server builds the first user message of the thread from the rebuilt context and nothing else:

```
Context supplied by the application. It is the scope of the question. Do not assume anything not listed.
<rendered.text: readable lines of every included item, including the definitions item>
{"entry_surface":"register_row","eon_id":null,"metric_id":"M325402","reporting_monthend_date":"2026-10-31","active_filters":{},"user_question":"<the user's message as an escaped JSON string>"}
MA2-REF v1 agent=data request=<clientRequestId> ctx=<first 12 characters of contextHash> definitions=<definitionsVersion>
```

- `reporting_monthend_date` is always the resolved `scope.month`. The user's question is inserted with a JSON encoder, so it cannot close the string or add fields; it is never concatenated into the readable lines.
- Scoped surfaces map to `register_row`; `general` and `dashboard` map to `general` (the field set the Data agent was validated with; VERIFIED in the `A2_CONTEXT` run). A message with readable lines before the JSON line has not been run yet (ASSUMPTION A-3, first live test).
- The last line is an application reference. It lets the backend recognise its own messages in a thread (duplicate suppression, 5.5.5) and shows the conversation's provenance when it is reopened. It is removed before a user message is displayed.
- Both agents receive the same text; the agent is picked after the review and does not change it.
- Follow-up messages are sent as plain user turns on the same thread (`thread_id`, `parent_message_id` = the last message in the thread, A-10). The thread, not the backend, holds the history, so no turns are replayed by the backend.

### 5.4 Conversations

A conversation belongs to exactly one agent for its whole life, because the thread was created for that agent and the handle records it. To use the other agent the user starts a new conversation and goes through context review again.

#### `POST /agents/conversations`

```ts
{ agentKey: 'analysis' | 'data'
  message: string                      // 1..2000 characters after trimming
  context: ContextRequest              // the request the user reviewed (5.3)
  contextHash: string                  // the hash the user reviewed; verified by rebuilding the context
  clientRequestId: string }            // uuid; duplicate suppression (5.5.5)
```

- Response `202`: `{ conversation: Conversation; userMessage: Message; run: Run }`. The response is returned as soon as Snowflake accepted the background run (the step that creates the thread is described in 5.5.3).
- Errors: `400 VALIDATION_FAILED | MESSAGE_TOO_LONG | CONTEXT_INVALID | CONTEXT_TOO_LARGE`, `404 METRIC_NOT_FOUND | APPLICATION_NOT_FOUND`, `409 CONTEXT_STALE | IDEMPOTENCY_KEY_REUSED`, `429 AGENT_BUSY | RATE_LIMITED | AGENT_BUDGET_EXHAUSTED`, `503 AGENT_UNAVAILABLE | THREAD_UNAVAILABLE`.

```ts
interface Conversation {
  conversationId: string               // opaque signed handle (3.8); the only identifier the browser uses
  threadId: number                     // the Snowflake thread id, informational; never accepted without the handle
  agentKey: 'analysis' | 'data'
  title: string                        // first 60 characters of the first user message
  entrySurface: ContextRequest['entrySurface']
  scope: { month: Month; metricId: string | null; eonId: string | null }
  chips: string[]                      // the originating context, from the thread's first message
  contextHash: string                  // hash recorded in the thread's application reference
  messageCount: number
  createdAt: string; updatedAt: string // from the thread
}
```

#### There is no conversation list endpoint

The list of conversations is browser-local (below). The backend cannot enumerate "my" threads, by design (POC limitation, OI-13).

#### `GET /agents/conversations/{conversationId}`

Verifies the handle, reads the thread (`THREAD_MESSAGES`), parses it and returns `{ conversation, messages: Message[], activeRun: Run | null }`. Messages are returned in order (at most 26, because a conversation allows 12 user messages). `activeRun` is present when the last user message has no assistant answer yet. `GET /agents/conversations/{conversationId}/context` returns the context summary recovered from the first message (readable lines and chips) for the grounding rail. Errors: `404 CONVERSATION_NOT_FOUND` (bad or tampered handle, or the thread no longer exists), `503 THREAD_UNAVAILABLE`.

#### `POST /agents/conversations/{conversationId}/messages`

Body `{ message, clientRequestId }`. The agent is taken from the handle; a body field `agentKey` is not accepted. Response `202 { userMessage, run }`. A conversation has at most one active run: a second submit returns `409 RUN_IN_PROGRESS` with `details.runId`. A conversation allows at most 12 user messages; beyond that `400 VALIDATION_FAILED` with `details.reason = "CONVERSATION_LIMIT"` and the UI offers to start a new conversation.

#### Browser conversation metadata (`localStorage`, key `ma2:conversations`)

The browser stores only a lightweight index. It never stores messages, SQL or result rows.

```ts
interface SavedConversation {
  conversationId: string               // the handle
  threadId: number
  agentKey: 'analysis' | 'data'        // selected agent; the handle also carries it and wins
  title: string
  createdAt: string
  lastActivityAt: string
  contextSummary?: { chips: string[]; entrySurface: string }   // optional
  lastRunId?: string                   // so a refresh can resume polling
}
```

Rules: at most 50 entries (oldest by `lastActivityAt` dropped); updated on create, on send and on each completed run; opening an entry calls `GET /agents/conversations/{id}` and renders the backend's messages; a `404` marks the entry "no longer available" and offers to remove it. The Investigation pages keep the run id of their last analysis under `ma2:analysisRun:<kind>:<id>:<month>`. Known limitation: the list exists only in that browser profile; it is not shared across browsers or devices, clearing site data loses it (the threads remain in Snowflake), and there is no server-side "archive" because there is no registry; "Remove" deletes the local entry only.
**What the browser retains.** The conversation handle (`conversationId`), the `SavedConversation` fields above, and the latest run token (`lastRunId`, and `ma2:analysisRun:*` on the Investigation pages). The run token carries `threadId`, `agentKey`, `userMessageId`, `snowflakeRunId` and `submittedAt` (5.5.3). The browser does not store message text, SQL, rows or message ids; those are read back from the thread. After a backend restart the same token is enough: the server opens a new Snowflake connection and reads the thread. That recovery was checked by closing the connection that submitted a run and reading the finished thread from a new connection (5.5.6).

### 5.5 Runs: execution architecture, state model, polling (REVISED, DEC-02, DEC-15)

Polling is how the browser learns about a run. It is not the execution architecture, which is defined here.

#### 5.5.1 Requirements and how they are met

| Requirement | How |
| --- | --- |
| A submission returns an execution id promptly | `DATA_AGENT_RUN` with `background: true` returns `status: in_progress` and a `run_id` immediately; the API returns a run token (below) in the same request |
| Blocking Snowflake calls do not block the event loop | Every V2 route is a plain `def` (Starlette runs it in its thread pool); the submit call is short; polls are coalesced and cheap; the long agent work runs inside Snowflake, not in this process |
| State and results are persisted | In the Snowflake thread (messages, tool calls, executed SQL results) |
| Concurrency is bounded | At most 4 background runs in flight per process (in memory), one active run per thread, per-handle and global rate and budget counters (5.6) |
| A browser disconnect does not destroy an accepted run | The run executes in Snowflake "even if the client disconnects" (documented) |
| A container restart has defined recovery | The run token is self-contained and the truth is in the thread, so the state is recomputed after a restart (5.5.6) |
| Duplicate submissions and retries do not run twice by accident | 5.5.5 |

The existing backend call already passes `TRUE` as the third argument (`agent_client.py`). Stored validation files show `thread_id: null` because `response_parser._thread_id` keeps a thread id only when it is a top-level string. Snowflake returns an integer at `metadata.thread_id`. Those files do not show that creation failed.

`THREAD_MESSAGES` lists messages newest first. Message ids are not in time order: a user message id was numerically larger than the assistant message that followed it. Calling `THREAD_MESSAGES(thread, 2, newestId)` returned the next two older messages. Calling it with the oldest id returned none. `last_message_id` of 0 is rejected. Polling therefore reads the whole thread (measured about 0.15 s) and finds the assistant whose `parent_id` equals the run's `user_message_id`. REST thread creation was not required and was not called.

#### 5.5.3 Execution flow (the call that ran)

Every call is:

```sql
SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN(%(agent)s, %(body)s, TRUE)
```

The agent name is a server constant. The third argument stays `TRUE`. `"stream": false` is sent and was accepted; `"stream": true` is not used.

1. **Validate.** Check the handle or `agentKey`, message length, limits and the in-flight cap. A follow-up is refused with `409 RUN_IN_PROGRESS` while the thread's `metadata.status` is `IN_PROGRESS`.
2. **First message of a conversation.** Body, with no `thread_id` and no `parent_message_id`:

```json
{ "messages": [{ "role": "user", "content": [{ "type": "text", "text": "<context text, the MA2-REF line, and the user's message>" }] }], "stream": false, "background": true }
```

3. **Follow-up.** Read the thread, take `metadata.last_message_id` (the newest message, which is an assistant message when the thread is idle), and send:

```json
{ "thread_id": "<threadId>", "parent_message_id": "<lastMessageId>", "background": true, "stream": false, "messages": [{ "role": "user", "content": [{ "type": "text", "text": "<the user's message only>" }] }] }
```

`<threadId>` and `<lastMessageId>` are the integers from the thread. Do not send 0: `THREAD_MESSAGES` rejects a `last_message_id` of 0, and a follow-up parent of 0 was not the call that was tested. The request body cannot choose the agent; the handle's agent is used.
4. **Accept.** The function returns within about a second: `{ "status": "in_progress", "metadata": { "thread_id", "run_id", "user_message_id" } }`. `run_id` is `{threadId}-{userMessageId}`. The API returns `202` with a signed run token `{ threadId, agentKey, userMessageId, snowflakeRunId, submittedAt }`.
5. **Completion.** `SELECT SNOWFLAKE.CORTEX.THREAD_MESSAGES(<thread_id>)`. While the run is going, `metadata.status` is `IN_PROGRESS`. It becomes `IDLE` when the assistant reply is stored. The reply is the message with `role = assistant` and `parent_id = user_message_id`. Its `message_payload` is a JSON string; parse it and pass the object to the parser (6.4). `message.agent.name` must equal the handle's agent.
6. **Retry.** Allowed when the run is `FAILED` and is the latest in the thread. Send the same user text again with `parent_message_id` equal to that run's `user_message_id` when no assistant child exists, otherwise equal to `metadata.last_message_id`. A user-message id was accepted as a parent in the probe (a sibling branch). The linear chain uses the newest id, which is what the UI sends.

Option C (an in-process worker around a synchronous call) and the REST Threads API are not used. Both were the fallback if this call failed. It did not fail for either agent.

#### 5.5.4 State model

The state is a function of the token, the clock and the thread; it is recomputed on each read.

| `status` | Condition | Notes |
| --- | --- | --- |
| `RUNNING` | No assistant message has `parent_id` equal to the token's `userMessageId`, and elapsed time is under `failAfterMs`. The thread's `metadata.status` is `IN_PROGRESS` during this time | After `overdueAfterMs` (180 s) the run is still `RUNNING` and `overdue` is `true` |
| `COMPLETED` | An assistant message with `parent_id` equal to `userMessageId` is present. Parse its `message_payload` | `message` carries the parsed content. Do not treat a numerically larger message id as "later": ids are not in time order |
| `FAILED` | The assistant payload records an error (`AGENT_EXECUTION_ERROR`), cannot be parsed (`AGENT_RESPONSE_UNPARSEABLE`), the thread is `IDLE` with no assistant child (`AGENT_EXECUTION_ERROR`; not observed in the probe), or no child exists `failAfterMs` (600 s) after submission (`AGENT_TIMEOUT`) | `retryable: true` |
| (read error) | The thread cannot be read | `503 THREAD_UNAVAILABLE`; the run itself is not affected, the client retries the read |

There is no `QUEUED` and no `CANCELLED` state. Snowflake accepts the background call immediately. Transitions are `RUNNING -> COMPLETED` or `RUNNING -> FAILED`.

#### 5.5.5 Duplicates, retries, concurrency

- **Duplicate submission.** `clientRequestId` is remembered in memory for 1 hour. The same id with the same request returns the stored response and starts nothing; the same id with a different request returns `409 IDEMPOTENCY_KEY_REUSED`. After a restart the memory is empty, so a repeated submit can create a second thread or a second follow-up. That is accepted for this demo: it is rare, and the extra message stays in its own thread or as another turn.
- **One active run per thread.** A follow-up is refused with `409 RUN_IN_PROGRESS` while `metadata.status` is `IN_PROGRESS`. That is the signal observed on 2026-11-04. Message ids are not used to decide which message is newer.
- **In-flight cap.** At most 4 runs submitted and not yet seen complete by this process; above that `429 AGENT_BUSY` with `retryAfterMs`. The count is in memory and rebuilt lazily (it restarts at 0 after a restart, which is acceptable because Snowflake does the work).
- **Retry.** `POST /agents/runs/{runId}/retry` is allowed when the run is `FAILED` and retryable and is the latest in its thread. It re-sends the original user text (read from the thread) as a new user message whose application reference includes `retry-of=<snowflakeRunId>`. A second retry of the same run finds that reference and returns the existing retry run (`200`) without submitting. A retry after `AGENT_TIMEOUT` can lead to two answers if the first one arrives late; both stay in the thread and the UI shows both.

#### 5.5.6 Restart and failure behaviour

| Event | Behaviour |
| --- | --- |
| Browser tab closed or refreshed | The run continues in Snowflake. The browser keeps `lastRunId`; on load it calls `GET /agents/conversations/{id}` and resumes polling the run |
| API container restarted while a run is in Snowflake | Nothing is lost: the run token is self-contained and the answer lands in the thread. The next poll recomputes the state. In-memory duplicate cache, in-flight count and rate counters reset |
| Snowflake slow | `RUNNING`, then `overdue`, then `FAILED / AGENT_TIMEOUT` after 600 s (retryable) |
| Agent returns an error | `FAILED / AGENT_EXECUTION_ERROR` (retryable) |
| Agent gate open (recent upstream failures) | New submissions are refused with `503 AGENT_UNAVAILABLE`; existing runs are unaffected |
| Thread unreadable | `503 THREAD_UNAVAILABLE` on the read; client retries |
| User presses "Stop waiting" | Client only: the page stops polling. The run is **not** cancelled in Snowflake (no SQL cancel exists); the answer appears in the thread when ready and in the conversation when it is reopened (OI-15) |
| In-process worker | Not used. A background run kept running after the submitting connection was closed, and the answer was read from a new connection |

#### 5.5.7 Browser contract: polling

```ts
interface Run {
  runId: string                        // opaque signed run token
  conversationId: string; agentKey: 'analysis' | 'data'
  status: 'RUNNING' | 'COMPLETED' | 'FAILED'
  overdue: boolean                     // true after overdueAfterMs while RUNNING
  attempt: number; retryOf: string | null
  submittedAt: string; finishedAt: string | null
  elapsedMs: number                    // server-measured, wall clock
  pollAfterMs: number | null           // null when COMPLETED or FAILED
  events: Array<{ at: string; type: 'submitted' | 'running' | 'overdue' | 'completed' | 'failed'; detail?: string }>
  error: { code: string; message: string; retryable: boolean } | null
  message: Message | null              // the assistant message, present only when COMPLETED
}
```

- `GET /agents/runs/{runId}` verifies the token signature (a bad token returns `404 RUN_NOT_FOUND`) and returns the `Run`. A `COMPLETED` run carries `message` (section 6); the same message is in the conversation.
- **Coalescing.** The server reads the whole thread at most once per 2 seconds per thread, however many clients poll. A page cursor is not used: `last_message_id` walks toward older messages (5.5.2). A completed message is parsed once and kept in a bounded in-memory cache (50 messages, 30 minutes) for re-reads and CSV export; a cache miss re-reads the thread.
- `pollAfterMs`: 1,500 for the first 10 seconds of a run, 3,000 until 60 seconds, then 5,000; the client waits at least that long, pauses while the tab is hidden and polls once immediately when it becomes visible, and stops on a terminal status. After a network error or a `5xx` it backs off 2, 4, 8, 15 seconds; after 5 minutes of continuous failure it stops and shows "Connection lost. The run continues on the server. Reload to check."
- `events` come from the token time and the thread's message times; nothing is estimated. No percentage and no estimated time are shown (a client-side elapsed timer is allowed).
- `POST /agents/runs/{runId}/retry` follows 5.5.5 and returns `202 { run }`, or `200 { run }` for an existing retry, or `409 RUN_NOT_RETRYABLE`.
- Time limits: overdue 180 s, fail 600 s (5.6).

**Why polling and not streaming (PROPOSAL, from verified facts).**

1. A background run returns immediately and its output is read from the thread; there is no output stream on the SQL path (the SQL function returns a non-streaming response and rejects `stream: true`).
2. A long-lived stream through Cloudflare and Nginx on a single uvicorn worker (`--workers 1`, 512 MB) adds connections and failure modes for no extra information.
3. Because state is recomputed from the thread, polling needs no special handling for refresh, disconnect or restart.
4. If the REST streaming reconnect (`GET /api/v2/cortex/agent/runs/{run_id}`) is ever adopted with a token (option B), it can be added under the run without changing these contracts (OI-06).

### 5.7 Persistence, retrieval and recovery (REVISED, DEC-03)

| Concern | Where it lives |
| --- | --- |
| Conversation messages, tool calls, executed SQL and result sets, run completion | The Snowflake thread (source of truth) |
| Conversation list, titles, selected agent, thread id, timestamps, optional context summary, last run id | Browser `localStorage` (5.4) |
| Context | Not stored: recomputed from a structured request, then recorded in the first thread message (5.3) |
| Run state | Recomputed from the run token and the thread (5.5.4) |
| Duplicate suppression, poll coalescing, parsed-message cache, in-flight count, rate and budget counters | Process memory only; loss at restart is harmless by design (5.5.6) |
| Handle and token signing key | Derived at start-up (3.8); nothing stored |

There is no application database, no schema, no migration, no connection pool, no backup job and no volume. The Docker image, `docker-compose.yml` and `.env` need no change for persistence. Raw agent payloads are never kept beyond the bounded in-memory cache.

**Retrieval and refresh recovery.** On load the UI reads `ma2:conversations`; opening an entry calls `GET /agents/conversations/{id}`; if `activeRun` is present it resumes polling. A missing thread returns `404 CONVERSATION_NOT_FOUND` and the UI offers a new conversation.

**Stated limitations (POC).** Conversation lists are per browser. Recovery after a restart is a new connection plus the run token: the probe read a finished background run that way. Rate counters and the duplicate cache reset at restart. Cancellation is not available. Thread retention is whatever Snowflake provides.

### 5.8 Definitions and agent instructions (resolves OI-04 and OI-09)

1. **One source of truth.** `app/portfolio/definitions.py` (2.4) is the only place formulas are written. It feeds (a) `GET /portfolio/definitions`, (b) the required `ground_rules` and `definitions` context items, and (c) a generated block of text for the agent specifications. Every response carries `meta.definitionsVersion`.
2. **Same rules for both agents.** The `definitions` item renders, for the surface's scope, each applicable definition with its id, formula, grain, scope, status (`provisional`, `assumption`, `documented_rule`) and limitations, plus the line "These definitions are provisional and are not client-confirmed." Both agents receive identical text (5.3).
3. **Provisional rates are allowed and labelled.** A rate may be calculated only as PD-01 for one metric, one month and one scope, shown with its numerator and denominator and the word "provisional", never compared across metrics and never described as client-confirmed. The same applies to derived numerator and denominator figures, denominator variants (PD-02) and the derived metric group (PD-19).
4. **Reporting month.** The backend resolves it (5.3) and supplies it in every first message. An explicitly selected month takes precedence. Neither agent's default month is ever used from V2.
5. **Agent specification v2 (a Snowflake change made with the demo account's ACCOUNTADMIN login in the implementation phase, after approval; not made here).** The implementation authors `snowflake/mock_data_setup/sql/20_agent_definitions_update.sql`, generated from the registry by `scripts/render_agent_spec.py`, which applies `ALTER AGENT ... MODIFY LIVE VERSION SET SPECIFICATION` (the upgrade path already written in `13_create_agent.sql`; syntax confirmed in the dry run, A-12) to both agents so that: the hard-coded default month `2026-10-31` is replaced by "use the supplied `reporting_monthend_date`; if none is supplied use the latest reporting month in the data and say so"; the Data agent's prohibition on `SUM(IS_NUMERATOR)/SUM(IS_DENOMINATOR)` is replaced by the same provisional-rate rule as the Analysis agent; and the generated definitions block with the token `DEFINITIONS_VERSION=<version>` is added to both. Existing agent objects and grants are kept.
6. **Until v2 is applied.** The first message already carries the month and the definitions block, so the hard-coded default never applies. The Data agent's older instruction may still lead it to decline a rate question; acceptance tests AG-9 to AG-14 record that as a known limitation (OI-04 residual) and do not block release unless the owner decides otherwise (DEC-17).
7. **Versioning.** `definitionsVersion` is `pd-<n>`. A snapshot test fails when the registry content changes without a version bump. The agent specification text includes the version token so an administrator can compare it with `meta.definitionsVersion` using `DESCRIBE AGENT`.

## 6. Agent response contracts (Part D)

### 6.1 Message

```ts
interface Message {
  messageId: string; conversationId: string   // messageId is the Snowflake thread message id
  role: 'user' | 'assistant'
  agentKey: 'analysis' | 'data'
  runId: string | null
  createdAt: string
  content: UserContent | AnalysisContent | DataExplorerContent
}
interface UserContent { kind: 'user'; text: string; contextHash: string | null }
interface ContentWarning { code: string; message: string }
```

`content.kind` is the discriminator. A conversation with `agentKey = analysis` only ever holds `analysis` assistant messages; with `data` only `dataset` ones. They are separate contracts because they render differently and must not be merged.

### 6.2 Data Explorer (`kind: "dataset"`)

```ts
interface DataExplorerContent {
  kind: 'dataset'
  interpretedIntent: string | null          // parsed from the agent's "Interpreted intent" section, null if absent
  assumptions: string[]                     // parsed from "Assumptions", [] if absent
  agentText: string                         // the agent's full prose, markdown; display only, never a data source
  noQueryExecuted: boolean                  // true when no SQL tool result exists
  queries: QueryResult[]                    // every SQL execution, in order
  primaryQueryIndex: number | null          // the last query with status 'success'
  warnings: ContentWarning[]
}
interface QueryResult {
  index: number
  toolUseId: string
  toolName: string | null
  sql: string | null                        // exactly json.sql from the tool result
  queryId: string | null                    // Snowflake query id from the tool result
  status: 'success' | 'empty' | 'error'
  error: { message: string } | null         // message bounded to 500 characters
  columns: Array<{ name: string; type: string; nullable: boolean | null; scale: number | null }>
  rows: Array<Array<string | null>>         // cells exactly as returned by the tool, in column order
  rowCount: number | null                   // resultSetMetaData.numRows
  rowsReturned: number                      // rows.length
  truncated: boolean
  truncation: { reason: 'RESULT_SET_LIMIT' | 'RESPONSE_CAP' | 'AGENT_ROW_LIMIT' | null; limit: number | null; note: string | null }
  exportable: boolean
}
```

The Data Explorer UI must show, for the primary query and for every other query on request: the **SQL panel** (`sql`, monospaced, read-only), the **results table** (`columns`, `rows`), the **row count** ("`rowsReturned` of `rowCount` rows", or "`rowsReturned` rows" when `rowCount` is `null`), a **truncation notice** whenever `truncated` is true, **Copy SQL** (client-side from `sql`), and **Export CSV**.

Truncation rules: `RESULT_SET_LIMIT` when `rowsReturned < rowCount`; `RESPONSE_CAP` when the backend's 1,000-row cap applied; `AGENT_ROW_LIMIT` when the SQL ends in `LIMIT n` and `rowCount == n` (heuristic: the agent adds `LIMIT 100` to row-level detail, VERIFIED in its instructions, so the total is unknown and the notice says so).

Export (supported): `GET /agents/conversations/{conversationId}/messages/{messageId}/queries/{index}/export` returns `text/csv; charset=utf-8`, attachment name `query-<index>.csv`, header row from `columns`, rows as returned by the thread. Cells beginning with `=`, `+`, `-` or `@` are prefixed with `'` to prevent spreadsheet formula injection. It exports only rows read from the thread message (from the in-memory cache or by re-reading the thread). When `truncated` is true the file name gets the suffix `-partial` (`query-<index>-partial.csv`). It verifies the handle and runs no SQL.

Not supported, deliberately: editing SQL, running user-typed SQL, "Run again" as re-execution of stored SQL, credit or timing figures from Snowflake (none is returned by the deployed tool results; only the server-measured `elapsedMs` of the run is shown). The prototype shows editable SQL, "Max 1,000 rows", a credit figure and tables that do not exist (`FACT_METRIC_OBSERVATION`, `V_MOVEMENT`, `DIM_ORG`). None of those are in this contract. "Run again" in the UI means retry (5.5).

### 6.3 Analysis & Investigation (`kind: "analysis"`)

```ts
interface AnalysisContent {
  kind: 'analysis'
  text: string                              // the agent's answer, markdown
  evidence: QueryResult[]                   // every SQL the agent executed, same shape as 6.2, rows capped at 200
  toolActivity: Array<{ toolUseId: string; toolType: string; toolName: string | null; status: 'RESULT' | 'ERROR' | 'NO_RESULT' }>
  suggestedFollowUps: string[]              // from suggested_queries blocks, plain strings, max 5
  notices: Array<{ code: 'AGENT_GENERATED'; text: string }>   // always present
  warnings: ContentWarning[]
}
```

Rendering rules: the answer text sits under a standing notice "Agent-generated. Explanations of cause are hypotheses until validated." Evidence is shown as "Show query and evidence" with the real SQL and rows. There is no "Established" badge on agent prose, because no validator exists for these two agents (the DQ narrative validator is specific to the DQ agent). Charts are not produced. Numbers in the prose that are not in the evidence are not verified by the API.

### 6.4 Parser rules (fixing the existing defect)

Defect (VERIFIED): `backend/app/cortex/response_parser.py` returns only the text items of the last assistant message and discards `tool_use` and `tool_result` items, so `system_execute_sql` results are lost. That parser stays unchanged for the DQ path. V2 adds a separate parser (`app/agents/parse.py`) with these rules.

1. Input is one assistant message. From `THREAD_MESSAGES`, parse the `message_payload` string (it is JSON text even when `is_compressed` is true) and use that object. A synchronous `DATA_AGENT_RUN` response is already that object (`role`, `content`, `metadata`). Locate `content` on the object. Do not look for a top-level string `thread_id`; the id is the integer `metadata.thread_id`.
2. Scan **all** assistant messages and **all** content items in order, assigning each a block index. Text items are concatenated in order into the prose.
3. Handled item types: `text`; `thinking` (dropped: never stored, never shown); `tool_use` (recorded with id, tool name, tool type, status); `tool_result` (matched by `tool_use_id`); `suggested_queries`; `data_to_chart` (recorded in `toolActivity` only, not rendered, warning `CHART_NOT_RENDERED`); any other type increments a counter and adds warning `UNKNOWN_BLOCK_TYPE`. Nothing is dropped silently.
4. A `tool_result` whose content has a `json` item with `sql` or `result_set` yields one `QueryResult`. Fields, using the shape read on 2026-11-04: `sql` from `json.sql`; `queryId` from `json.query_id`; `rows` from `json.result_set.data`; `rowCount` from `json.result_set.resultSetMetaData.numRows`; `columns` from `json.result_set.resultSetMetaData.rowType[]` (`name`, `type`, `nullable`, `scale`). The same `numRows` and `rowType` are also accepted one level up, at `json.resultSetMetaData`, if a response uses that shape.
5. Correlate `tool_use` and `tool_result` by `tool_use_id`. A result without a use is kept with warning `ORPHAN_TOOL_RESULT`. A use without a result becomes `toolActivity` status `NO_RESULT` and warning `RESULT_NOT_RETURNED`.
6. Multiple blocks and multiple SQL executions are all kept, in appearance order. `primaryQueryIndex` is the last `success`. Warning `MULTIPLE_QUERIES` is added when there is more than one.
7. A tool result with an error status or an `error` field yields `status: 'error'` with a bounded message; warnings in the result are copied to `warnings`.
8. Datasets are never reconstructed from prose. If prose contains a table but no result set exists, `queries` stays empty, `noQueryExecuted` is true when no SQL tool was used at all, and the prose is shown only as agent text.
9. Cell values are kept as the strings the tool returned (VERIFIED from `executed` results in `agent_preview_results.json`: every value is a string, such as `"923"`). The same results show that a SQL `NULL` arrives as an empty string (for example `TEST_RESULT` is `""` for a pending test). The parser does not guess: `rows` carries exactly what was returned, `null` only if the tool returned JSON `null`, and the UI renders an empty cell as empty, not as the word "null" or zero.
10. Caps (what the API returns): 1,000 rows per query (200 for analysis evidence), 5 MB per message. Exceeding a cap sets `RESPONSE_CAP` truncation and a warning; it never fails the run. The complete result stays in the thread.
11. Unparseable or empty responses fail the run with `AGENT_RESPONSE_UNPARSEABLE` (retryable). Only block-type counts and the payload length are logged.
12. `interpretedIntent` and `assumptions` use a tolerant match on the markdown headings the Data agent is instructed to use (`Interpreted intent`, `Assumptions`). They are display aids and may be `null` or empty.

### 6.5 Observation, derived metric, hypothesis in agent output

- Observation: `evidence[].rows` and `queries[].rows` (what Snowflake returned).
- Derived: values the application computes and labels (for example PD-01), which appear in the context, not in agent output.
- Hypothesis: any explanatory claim in `text`. The API does not split prose into "established" and "hypothesis". The UI treats the whole answer as agent-generated and says so. Sections an agent labels "Hypothesis" are displayed as written.

### 6.6 Failures and warnings

| Where | Code | Meaning | Retry |
| --- | --- | --- | --- |
| Run | `AGENT_TIMEOUT` | No answer 600 s after submission (a late answer still appears in the thread and turns the run into `COMPLETED`) | yes |
| Run | `AGENT_UNAVAILABLE` | Gate open after repeated upstream failures; no answer is produced | yes after cooldown |
| Run | `AGENT_EXECUTION_ERROR` | Snowflake raised an error for the agent call; generic message, type logged | yes |
| Run | `AGENT_RESPONSE_UNPARSEABLE` | Response had no assistant message or was not JSON | yes |
| Run | `WORKER_LOST` | Not produced. Execution is a Snowflake background run, not an in-process worker | no |
| Submit | `CONTEXT_STALE` | The rebuilt context differs from the one the user reviewed (data, definitions or request changed) | no (review again) |
| Submit | `AGENT_BUSY`, `RATE_LIMITED`, `AGENT_BUDGET_EXHAUSTED` | Capacity, rate or budget limit | yes after `retryAfterMs` |
| Message | `NO_QUERY_EXECUTED` | The agent ran no SQL (for example it asked a clarifying question or refused a write request) | not an error |
| Message | `QUERY_ERROR` | At least one query returned an error | not a run failure |
| Message | `TRUNCATED` | At least one query was truncated | not an error |
| Message | `RESULT_NOT_RETURNED`, `ORPHAN_TOOL_RESULT`, `UNKNOWN_BLOCK_TYPE`, `CHART_NOT_RENDERED`, `MULTIPLE_QUERIES` | Parser observations | not errors |

An agent or tool failure never produces fabricated content. The run is `FAILED` or the message carries an honest warning, and the UI shows that. The only permitted substitution is the labelled precomputed analysis of 6.7, on the two Investigation pages and nowhere else.

### 6.7 Precomputed investigation analyses (static fallback)

**Why.** An agent run can take longer than a user will wait. As in the legacy application, which served packaged and previously computed analyses when the live path was slow or down, the two Investigation pages can show an analysis that was computed earlier by the same agent, clearly labelled as such, while the live run continues.

**Scope.** Only `agentAnalysis` of 4.20 (metric-scoped) and 4.21 (application-scoped). Chat conversations never use it: a slow or failed chat run stays honest (running, failed, retry).

**Assets.** Files under `backend/app/fallback_assets/v2/investigations/` (`metrics/<METRIC_ID>.json`, `applications/<EON_ID>.json`) and a `manifest.json` with each file's SHA-256, the generation date and the dataset and definitions versions. Coverage: one file per metric (24) and the applications chosen by the generator's fixed rule (PROPOSAL, DEC-20: the 50 applications that are non-compliant in the latest month ordered by open findings (PD-07) descending, then `EON_ID`). A target with no file has no fallback.

```ts
interface PrecomputedAnalysis {
  source: 'precomputed'
  target: { kind: 'metric'; metricId: string } | { kind: 'application'; eonId: string }
  month: Month
  generatedAt: string
  datasetVersion: string; definitionsVersion: string; agentSpecVersion: string | null
  stale: boolean; staleReason: 'DATASET_CHANGED' | 'DEFINITIONS_CHANGED' | null
  label: string                          // "Pre-analysed, generated on <date>. Not a live run."
  content: AnalysisContent               // exactly the shape of 6.3, including evidence rows
}
```

**Generation.** A script, `scripts/generate_precomputed_investigations.py`, runs once per target through the normal path (internal call of the context builder for `metric_investigation` or `application_investigation` with default items, a new thread and background run, the parser of 6.4, the registry definitions) with a fixed question per kind held in the script. It uses the backend's existing Snowflake login (ADMIN, 1.5) and makes about 74 agent calls, a few at a time. A person reviews the output and accepts or rejects each file; no file is edited by hand and none is written from a template. A test compares file hashes with the manifest.

**When it is served** (computed on each read of 4.20 and 4.21 from the `runId` parameter, the target and the requested month; the file's month must equal the requested month):

| The run identified by the `runId` parameter | `agentAnalysis.status` |
| --- | --- |
| no `runId` | `NOT_RUN` (or `FALLBACK_STATIC` when `fallback=precomputed` is sent and a file exists) |
| `RUNNING`, elapsed under 45 s | `RUNNING` |
| `RUNNING`, elapsed 45 s or more, file exists | `FALLBACK_STATIC` (the live run continues) |
| `FAILED` (any code), file exists | `FALLBACK_STATIC` |
| `FAILED`, no file | `FAILED` |
| `COMPLETED` | `COMPLETED`, `source: 'live'`; the precomputed content is no longer returned |

The 45 s threshold is a constant (5.6), well below the 600 s point at which a run fails. Retry stays available while a fallback is shown, and the user may keep waiting for the live run ("Stop waiting" is client-side only). When a live run completes, the next poll returns `COMPLETED` and the page replaces the static content.

**Honesty rules.** The UI shows the label from `PrecomputedAnalysis.label` and the standing agent-generated notice (6.3). If `stale` is true (the file's dataset or definitions version differs from the current one) the file is still served, with a stronger notice and the reason. Numbers in the text are not verified by the API; the evidence rows are those stored in the file. Precomputed content is never mixed into live messages and is never stored in conversations.

Rules for rendering:

- The frontend never recomputes a rate, share, count or delta. It formats numbers sent by the API (`Intl.NumberFormat`, 1 decimal for rates shown as percent, integers with thousands separators).
- Every field with a lineage entry whose status is not `source` shows a chip: "Provisional", "Assumption", or "Not available", linked to `/definitions#PD-xx`.
- `null` renders as an em dash with an accessible label, never as 0.
- A month with `observed: false` renders hatched with the text "Not observed".
- Loading, empty, error and retry states are per card. A failed card does not blank the page.
- A response with `source = "packaged"` or any `warnings` shows a page-level notice.
- Agent results render by `content.kind`. An unknown `kind` renders the text and a note, not a blank.

Storage keys used by V2 are all prefixed `ma2:` (`conversations`, `analysisRun:<kind>:<id>:<month>`, `ctx`). Legacy uses `ma-dq-run:` and other keys without that prefix, so the two apps do not read each other's state.
